# Redis 分散式鎖重點筆記

> 整理日期：2026-07-28

---

## 1. 基本實作

- 最常見指令：`SET key value NX EX timeout`
- 進階：Redisson（推薦）、Redlock（多實例）

## 2. 為什麼無法保證強一致性？

1. **非同步複製**：Master 寫入成功後，資料尚未同步到 Slave 就發生 failover，新 Master 可能沒有這把鎖。
2. **網路分區**：客戶端與 Redis 斷線，但業務仍在執行，鎖因 TTL 過期被其他人搶走。
3. **依賴 TTL**：時鐘漂移、GC、業務執行時間過長都可能導致鎖提前失效。
4. **Redlock 限制**：雖然提高了可靠性，但仍非真正的共識演算法，無法提供線性一致性。

## 3. 可重入性

- **原生 SET NX**：不可重入。
- **Redisson**：支援可重入（使用 Hash 記錄 clientId + 重入次數）。

## 4. Watchdog 自動續期

- 解決業務執行時間超過鎖 TTL 的問題。
- Redisson 預設在未指定 leaseTime 時啟動 Watchdog，定期延長鎖的過期時間（預設約每 10 秒續期一次，每次延長 30 秒）。
- 客戶端崩潰或呼叫 unlock 後 Watchdog 停止，鎖最終會過期（防死鎖）。

**重要**：只有在使用 `lock.lock()`（不指定時間）時才會啟用 Watchdog。如果使用 `lock.lock(10, TimeUnit.SECONDS)` 則不會啟動。

## 5. 適用場景

- 高併發、對效能極度敏感
- 可接受極少數重複執行的業務（秒殺、庫存扣減、限流、非核心任務調度）

## 6. 實務建議

- 強烈建議使用 **Redisson**，不要自己用原生指令寫。
- 一定要設定合理的過期時間 + Watchdog 自動續期。
- 解鎖時必須驗證 value（防止誤刪別人的鎖）。
- 分散式鎖只能解決互斥，無法解決業務冪等問題。
